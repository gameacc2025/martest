# وضعیت صفحات حساب مشتری و استعلام‌های Website

**تاریخ:** 2026-11-04  
**دامنه:** Website / CUSTOMER  
**وضعیت:** بهبود رابط و کنترل دسترسی سمت Router؛ سرویس‌های موجود استفاده می‌شوند.

## آدرس‌های مشتری

صفحه `/profile/addresses` از endpointهای واقعی `/addresses` استفاده می‌کند. Backend این مسیرها را با `requireAccessType('CUSTOMER')` محافظت کرده و همه عملیات را به شناسه کاربر احراز هویت‌شده محدود می‌کند.

بهبودهای این مرحله:
- تبدیل ارقام فارسی و عربی شماره تماس و کد پستی به ارقام ASCII پیش از ارسال API.
- اعتبارسنجی ورودی‌های ضروری و محدودیت طول شماره تماس مطابق schema سرور.
- اعتبارسنجی کد پستی در صورت ورود؛ فقط رقم پذیرفته می‌شود.
- جلوگیری از ارسال تکراری درخواست تغییر آدرس پیش‌فرض و نمایش وضعیت عملیات.
- نمایش خطای اعتبارسنجی در فرم، بدون ارسال درخواست نامعتبر.

## پروفایل

صفحه `/profile` از context احراز هویت برای نمایش مشخصات استفاده می‌کند. قرارداد واقعی Backend بررسی شد:
- بارگذاری اولیه صفحه از `GET /auth/me` استفاده می‌کند و context جداگانه `user/profile/accessProfile/roles/permissions` را می‌گیرد؛ endpoint مستقل `GET /settings/profile` نیز اطلاعات هویتی، Profile، AccessProfile و نقش‌ها را برمی‌گرداند.
- `PATCH /settings/profile` فقط firstName/lastName/avatar را روی Profile تغییر می‌دهد؛ ایمیل و شماره تماس در این endpoint قابل ویرایش نیستند.
- `PATCH /settings/change-password` رمز فعلی را بررسی می‌کند، رمز جدید را hash می‌کند و RefreshTokenهای قبلی را باطل می‌کند.
- `POST /settings/profile/avatar` اکنون فایل واقعی JPEG/PNG/WebP را با سقف ۱ مگابایت اعتبارسنجی و ذخیره می‌کند؛ نام فایل تصادفی است و امضای باینری فایل نیز بررسی می‌شود. فایل قبلی پس از ثبت موفق URL پاک‌سازی می‌شود.
- `DELETE /settings/profile/avatar` مقدار آواتار را پاک و فایل محلی قبلی را حذف می‌کند.

ذخیره آواتار روی دیسک محلی backend انجام می‌شود. volume با نام `user_uploads` در Docker production به `/app/uploads` متصل شده تا فایل‌ها پایدار بمانند. در توسعه، پوشه `backend/uploads` به‌واسطه bind mount پروژه روی میزبان باقی می‌ماند. برای چند replica یا استقرار چندسروره، object storage مشترک باید جایگزین این ذخیره‌سازی محلی شود.

## مرکز استعلام مشتری

صفحه `/my-inquiries` از APIهای موجود استعلام استفاده می‌کند. اصلاحات این مرحله:
- جلوگیری از نمایش پاسخ دیررس درخواست استعلام قبلی پس از جابه‌جایی سریع بین جزئیات استعلام‌ها.
- پاک‌سازی پیام پیش‌نویس، انتخاب شرکت و وضعیت پیامک هنگام تغییر استعلام.
- حذف گزینه‌های تکراری شرکت دریافت‌کننده در صورت وجود چند پاسخ از یک شرکت.
- انتخاب خودکار شرکت در حالتی که تنها یک شرکت پاسخ‌دهنده وجود دارد.
- نمایش خطای دریافت پیام‌ها به‌جای نمایش اشتباه وضعیت «هنوز پیامی ثبت نشده» و امکان تلاش مجدد.

قواعد محرمانگی پاسخ‌ها، سهمیه پیام و SMS همچنان توسط API کنترل می‌شوند؛ UI مرجع مجوز یا سهمیه نیست.

## کنترل دسترسی مسیرها

مسیرهای پروفایل، دفترچه آدرس و استعلام‌های ارسالی در Website اکنون customer-only هستند. اگر حساب COMPANY یا STAFF مستقیماً URL این صفحات را باز کند، Router آن را از طریق PKCE به مسیر متناظر در پنل خودش هدایت می‌کند. این کنترل UX است؛ مجوز نهایی همچنان باید در Backend enforce شود.

## محدودیت بررسی

در مرحله تکمیلی پروفایل، Backend settings service/controller و volume ذخیره فایل تغییر کردند؛ Prisma schema و migration تغییر نکردند. تست‌های Node برای اعتبارسنجی و ذخیره آواتار نوشته/به‌روزرسانی شدند اما اجرا نشده‌اند. تست Vitest، build و browser test نیز اجرا نشده‌اند.
